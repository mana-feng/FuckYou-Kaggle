03 · 用户怎么查看和填写：页面不是一张海报

⏱ 14 分钟 ｜ 页面负责让人看懂并完成动作

🎯 一句话

Page 的工作是把已经存在的数据和动作，按用户当下要完成的任务摆出来；它不是“把所有字段全放上去”。

🧭 先做三张够用的页面

页面 用户想完成什么 页面应该优先给什么
员工列表 找到一个人 姓名、部门、职位，以及进入详情的入口
员工详情 看清一个人 完整资料和相关部门
新建/编辑表单 填一名员工 必填字段、部门选择、保存和取消

注意这三张页面不是三种装饰风格，而是三种不同任务。列表追求扫得快；详情追求看得全；表单追求不填错。

🧱 页面和数据怎么接上

Mendix 页面上的文字框、表格和下拉框，都需要知道自己在显示或编辑哪个对象。

例如“姓名”输入框不是一个孤立的白框；它接的是“当前这位员工”的 Name 属性。部门下拉框也不是手写部门名称；它接的是前一章画出的员工—部门关系。

所以当页面出现“没有上下文”“选不到数据”之类的提示时，不必恐慌。先问一句：这个组件现在到底在操作谁？

🔍 一个好页面先帮用户少想一步

做员工表单时，可以用下面三条检查：

用户现在知道自己在编辑谁吗？
  • 新建和编辑的标题不要混在一起。
用户知道哪些不能不填吗？
  • 只把真正必要的字段设成必填。
保存之后会发生什么？
  • 回列表、留在详情，还是显示确认提示？选一个清晰的结果。

这三条比把按钮做得花哨重要得多。

🧪 跟着做：把 Employee 变成能看的界面

Mendix 可以根据 Entity 帮你生成基础页面。第一次学习时，先让它生成，再理解生成的每一块；这比从空白画布硬拖控件更容易建立对应关系。

第 1 步：从 Employee 生成起点

在 Domain Model 里选中 Employee，寻找生成 overview、data grid、data view 或 CRUD 页面一类的入口。不同版本叫法会略有不同，目标是一致的：让 Mendix 为 Employee 建一张列表和一张编辑/详情页。

生成时如果被要求选模块、导航或页面模板，选择当前员工管理模块和一个最基础的响应式页面模板即可。

你会得到什么：

页面部分 它在帮你做什么 现在要不要美化
Data grid / 列表 一次显示多名员工 先不美化，只保留关键列
New 按钮 创建一个新的 Employee 要保留，之后会改行为
Edit 按钮或行点击 打开当前员工 要保留，确认上下文能传过去
Data view / 表单 显示或编辑一名 Employee 要检查字段绑定
Save / Cancel 提交或放弃本次修改 要保留，下一章会接逻辑

第 2 步：把列表变成“找人页”

打开员工列表，只留下 FullName、JobTitle、IsActive，以及能看出部门的列。不要先把 Email、入职日期、内部状态、所有关系都堆进去。

此时问自己一个非常具体的问题：如果我要在 20 个名字里找到“小王”，我第一眼要扫什么？ 列表应该服务这个问题。

第 3 步：检查表单的“数据上下文”

点开编辑页的 Data view（通常是包住一组字段的大容器）。Properties 中应能看见它操作的对象是 Employee 或一个 Employee 参数。

然后逐个确认：

  • 姓名输入框连到 FullName；
  • 邮箱输入框连到 Email；
  • 日期控件连到 StartDate；
  • 在职状态连到 IsActive；
  • 部门控件连的是 Employee 与 Department 的关联，而不是手打文本。

看起来像“组件没有数据”的问题，十有八九是这里的上下文或属性绑定不对。

第 4 步：把“部门”做成选择，而不是填写

在表单中新增 Reference selector / 下拉选择器，并让它选择 Department。运行前你可能还没有部门数据，所以暂时看到空列表很正常；下一小段会手动建两条测试数据。

第 5 步：制造两条真实数据

运行应用，用 New 新建两个部门（如果还没生成部门页面，可以先用 Domain Model 对 Department 也生成一个简单管理页），例如“产品部”和“研发部”。然后新建两名员工，分别选择不同部门。

不要跳过这一步。空页面永远看不出关联是否真的工作；两条数据才会暴露“我把部门选择器连错了吗”。

🔁 用户在页面里走的完整路线

员工列表看到多个人，找到目标
→
员工表单新建或编辑一人
→
保存把这次改动交给应用处理
→
回到列表确认数据真的变了

现在最后两步可能仍由默认行为处理；下一章才会把“保存”拆开，加入我们自己的规则。

🧯 页面不如预期时，先看这四处

症状 最可能的原因 先检查哪里
列表空白 还没有数据，或数据源没指向 Employee 列表的 data source 和测试数据
字段无法编辑 当前页面是只读模式，或控件被禁用 Data view 模式、字段属性
选不到部门 Department 还没有对象，或选择器连错关联 Department 测试数据、association
保存后没看到新员工 保存后仍在表单，或列表没刷新 保存动作和返回/刷新行为

官方文档把页面、领域模型和应用逻辑分成同一条建模链：页面负责呈现，数据模型给它对象，逻辑处理动作。官方 App Modeling 总览

✅ 检查点

为什么不能把所有字段都扔进员工列表？

👀 看答案

因为列表的任务是快速找到人。字段太多会让扫描变慢；详细信息应该放进详情页或编辑页，按需要再打开。

⚡ 走神救援

  • 列表用来找，详情用来看，表单用来填。
  • 页面组件必须知道自己在显示或编辑哪个对象。
  • 好页面会减少用户需要猜的事情。
  • 下一步：让保存、校验和跳转按规则发生。
