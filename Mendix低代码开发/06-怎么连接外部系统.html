06 · 怎么连接外部系统：别让应用变成一座孤岛

⏱ 14 分钟 ｜ 先知道该找谁，不急着背协议

🎯 一句话

集成是在让两个系统交换信息；先说清“谁提供什么、谁需要什么、什么时候出错”，再决定用 REST、导入导出还是 Marketplace 组件。

🧭 员工工具最常见的三种连接

你的目标 更像哪种方式 先问的问题
从 HR 系统同步部门 REST 服务 对方提供什么地址和数据格式？
一次性导入历史员工表 文件导入 谁负责清洗重复、空值和错误行？
增加成熟的通用能力 Marketplace 模块或组件 版本、权限和维护者可靠吗？

不要把“能连上”误认为“集成完成”。真正完成意味着：数据含义对得上、失败时有处理办法、以后更新不会悄悄把旧数据弄乱。

🔁 用一张问题单代替一堆术语

在接任何外部系统前，先回答五个问题：

  1. 谁是数据的权威来源？
  2. 这次传的是一个对象，还是一批对象？
  3. 对方缺字段或返回错误时，应用怎么办？
  4. 同一条请求重试两次，会不会制造两名重复员工？
  5. 哪些凭据不能写在页面或流程里？

这些问题比“先选哪个连接器”更早，也更重要。

🧱 Marketplace 的正确位置

Marketplace 像一个经过社区或官方发布的零件库。它适合减少重复造轮子，例如常见连接器、界面组件或通用模块。

但装入一个模块不是“把问题交出去”。仍要看三件事：它是否兼容当前 Studio Pro 版本、它带来了哪些依赖、它要访问哪些数据或权限。对不熟悉的模块，先在小项目试，不要直接塞进重要应用。

🧪 先不连：把“同步部门”讲清楚

假设公司已经有一个 HR 系统，部门名单应以它为准。你希望 EmployeeHub 显示这些部门，但不希望两边各自乱改。

先把需求写成下面这个表。表填不出来，就还不应该动连接器。

问题 EmployeeHub 的示例答案
谁是权威来源？ HR 系统；EmployeeHub 只读取/同步部门
什么时候同步？ 每天凌晨，或管理员手动点击“同步部门”
对方给什么？ 部门编号、部门名称、负责人名称
本地怎么对应？ 用外部部门编号找到同一个 Department
对方暂时不可用？ 不覆盖旧数据，记录失败，让管理员稍后重试
同步两次会怎样？ 更新同一部门，不新建两条重复记录

这里已经出现了集成最核心的三件事：数据所有权、字段映射、失败策略。REST 只是实现它的其中一种工具。

🧭 三种常见做法，该怎么选

做法 A：一次性文件导入

适合：你只需要把历史 Excel/CSV 变成第一批 Employee 或 Department 数据。

跟做顺序：先拿 5 行脱敏样例 → 对照每一列映射到哪个属性 → 决定空值怎么处理 → 先导入测试环境 → 检查有没有重复或乱码 → 再导正式数据。

它的优点是简单、可控；缺点是不会自动持续同步。不要把“每周人工导文件”误称为实时集成。

做法 B：调用外部 REST 服务

适合：对方系统有稳定接口，你需要定期或按按钮拉取信息。

在 Mendix 中通常会经历：导入或描述服务 → 定义请求和响应的数据结构 → 调用服务 → 把响应映射到本地对象 → 处理成功和失败。先把对方提供的样例响应保存下来，再做映射；没有样例就不要猜字段名和日期格式。

第一版只做一个只读请求。 例如读取部门清单并显示。确认读对以后，再考虑把本地改动写回外部系统；“能写”会带来冲突和重复的额外责任。

做法 C：用 Marketplace 复用成熟能力

适合：你需要常见身份认证、Excel 导入、连接器或 UI 控件，而官方/社区已有维护中的模块。

安装前做 4 个检查：

  1. 支持的 Studio Pro 版本是否覆盖你现在的版本；
  2. 最近维护时间和发布者是否可信；
  3. 它会新增哪些模块与依赖；
  4. 它需要哪些权限、网络地址或密钥。

安装后先运行项目并读 Consistency Errors，再做一次最小功能测试。不要等到把它接进三条核心流程后才第一次运行。

🔐 凭据和个人信息放在哪里

不能这样做 为什么危险 应该怎么想
把密码或 API key 写在页面文字里 浏览器/截图/版本记录可能泄露 使用平台提供的受控配置或密钥管理方式
把完整员工信息随便写进日志 日志访问范围常比业务数据更广 只记必要的请求标识和错误摘要
失败时把原始响应直接展示给用户 可能暴露技术细节或敏感字段 给用户可行动提示，把技术细节留在受控日志

对于外部服务，安全不止是“连得上”。如果你发布 REST 服务给别的应用，Mendix 也支持不同认证方式，并会生成可交互的服务文档；这些能力需要和角色、数据范围一起设计。官方 Published REST Services 文档

🧯 集成失败时先问的四件事

现象 不要先假设 先查什么
调用失败 “一定是 Mendix 坏了” 地址、认证、网络、对方服务状态
返回成功但页面没数据 “接口没给数据” 响应映射是否把字段放进本地对象
同步后重复数据 “数据库坏了” 用来识别同一条外部记录的唯一编号
某些中文或日期不对 “页面显示问题” 对方格式、时区、字符编码和属性类型

本章的完成标准

你不用今天真的接上企业 HR 系统。只要能清楚回答：谁是部门数据的权威、我们何时拉取、用哪个外部编号去重、失败后保留什么并告诉谁，你已经比“只会点连接器”更接近可用的集成设计。

🛑 可以停在这里

集成的目标不是让你的应用连接得更多，而是让需要的数据和能力可靠地进来。最后一章把这个已经能用的应用跑起来、交付出去。

✅ 检查点

为什么在选 REST 或 Marketplace 之前，要先确定“谁是数据的权威来源”？

👀 看答案

因为两个系统都能改同一份信息时，迟早会出现冲突。先确定权威来源，才能知道谁负责更新、谁只是读取或同步，以及冲突该怎么处理。

⚡ 走神救援

  • 集成是两个系统交换信息，不是“连通了就结束”。
  • 先问数据来源、失败处理、重复请求和凭据放哪。
  • Marketplace 能省时间，但要看版本、依赖和权限。
  • 下一步：运行、测试、发布并和别人协作。
