05 · 谁能看见和修改什么：权限不是最后再加的锁

⏱ 14 分钟 ｜ 先定义边界，再放心交给别人用

🎯 一句话

安全的核心不是“给应用加一个登录页”，而是明确：不同角色能进入哪里、看哪些数据、执行哪些动作。

👥 先只分两种人就够了

角色 可以做什么 不应该做什么
普通员工 查看自己的信息，提交修改请求 看所有同事的资料，改部门结构
人事管理员 查看和编辑员工、部门 把管理功能暴露给未登录的人

角色不是人的名字。角色是一组权限；同一个人可以在不同应用里有不同角色。

🔐 三层边界，别只做一层

页面边界
  • 这个角色能不能打开“员工管理”页面？
数据边界
  • 打开后，能读到哪些员工和部门？
动作边界
  • 能不能执行保存、删除、导出这样的 Microflow？

只把“编辑”按钮藏起来不够。因为按钮是界面层；真正的数据和动作也要有对应的权限限制。

🧠 权限设计最容易犯的错误

“先全部打开，最后上线前再收紧”听起来省事，实际最容易漏。更稳的办法是先从最小权限出发：

  1. 先写清一个角色完成任务必须做什么；
  2. 只给这些必要权限；
  3. 用这个角色实际登录测试；
  4. 缺什么再补，不要一开始全开。

这不是故意为难自己。权限问题最怕“平时看不到，出事才发现”。

🧪 跟着做：先做一张最小权限表

先别急着在 Studio Pro 里勾选一大堆选项。拿一张纸或表格，写下这张最小表：

事情 普通员工 人事管理员
打开员工列表 只能看自己，或暂时不给 可以
新建员工 不可以 可以
编辑任意员工 不可以 可以
编辑自己的资料 以后可加 可以
维护部门 不可以 可以
调用保存流程 仅自己的修改流程 可以

这张表不是“文档工作”；它就是你稍后配置 Page、Entity、Microflow 权限时的答案来源。

第 1 步：区分 User Role 和 Module Role

在 App Security 里，User Role 是应用层给真实用户分配的身份，例如 Employee 和 HRAdmin。在模块 Security 里，Module Role 是这个模块理解的身份，例如 EmployeeUser、HRManager。

你可以先把它理解成两层翻译：

真实登录的人被分配 User Role
→
应用 User Role包含一个或多个模块角色
→
模块规则据此限制页面、数据、流程

初学时可以只建两套对应角色，不必先设计复杂的部门经理、区域经理、外包人员体系。

第 2 步：先开安全，再接受检查器“挑刺”

在 App Explorer 的 App > Security 中启用适合当前阶段的安全设置。练习时可以从原型/演示级别理解页面和 Microflow 的限制；真正交付前必须按生产级别补齐实体数据访问。官方说明明确：生产安全需要显式配置页面、Microflow、实体等访问，默认不是“自动安全”。App Security 文档

安全打开后出现一串未配置提示是正常的。它不是让你绕过的麻烦，而是一张待办清单：哪些页面、流程或实体还没有说明“谁能用”。

第 3 步：配置页面访问

打开员工列表、部门维护页和编辑页的 Properties，给它们分配允许访问的模块角色。

建议先做一个容易验证的差异：

  • HRManager 能从导航看见“员工管理”和“部门管理”；
  • EmployeeUser 暂时看不见部门维护，也不能进入任意员工编辑页。

隐藏导航只是体验上的第一层，后两层仍要继续配。

第 4 步：配置数据访问

在模块 Security 的 Entity access 中，分别看 Employee 和 Department。至少明确每个角色是否能读取、创建、修改和删除。

开始时可以设得保守：

实体 EmployeeUser HRManager
Employee 暂时无权或仅只读 读取、创建、修改；删除按需求再开
Department 无权或只读 读取、创建、修改

“员工只能看自己”需要把当前登录用户与 Employee 关联，再写约束；这是下一阶段的权限细化，不要假装一行勾选就已经实现了。

第 5 步：配置 Microflow 访问并测试

为 ACT_SaveEmployee 这类 Microflow 赋予合适角色。然后用两个测试用户登录，分别点击导航、打开页面、尝试保存。

测试标准不是“管理员能用就行”： 普通员工看不到不该看的；管理员能完成该完成的；两者都不会因为缺了一项隐藏权限而卡住。

🧯 三个非常容易被误解的地方

“有登录页”不等于“数据受保护”

登录只回答“你是谁”；实体访问规则回答“你能看哪条数据、改哪个字段”。页面、数据和流程是不同的门。

“按钮不见了”不等于“动作不能发生”

如果 Microflow 自己没有正确的访问限制，别的页面、链接或组件仍可能调用它。界面隐藏是减少误操作，不是完整防线。

“管理员”不等于应该拥有所有业务数据

管理员是技术管理身份，HRManager 是业务角色。真实项目里要把“能维护系统”和“能读员工信息”分开思考。

📋 上线前的五分钟权限演练

  1. 以每个角色各登录一次。
  2. 写下它应该能看到的导航项。
  3. 尝试打开一个不该看的页面。
  4. 尝试执行一个不该执行的保存/删除动作。
  5. 打开 Security 检查结果，优先解决明确的红色问题。

官方的安全模型也将限制分为页面、实体数据和 Microflow 等文档访问；只配其中一层并不完整。官方 Security 总览

✅ 检查点

为什么“把按钮藏起来”不能单独算安全设计？

👀 看答案

因为按钮只影响界面看起来像什么。真正安全还要限制页面入口、可读数据和可执行动作；否则有人仍可能通过其他路径调用不该做的操作。

⚡ 走神救援

  • 角色是一组权限，不是人的姓名。
  • 权限至少看三层：页面、数据、动作。
  • 从“完成工作所需的最小权限”开始，再用真实角色测试。
  • 下一步：让应用接入外部系统和可复用组件。
